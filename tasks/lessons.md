# 项目经验

## 2026-04-02

- 这个仓库做前端构建前，必须先执行 `nvm use 8.17.0`，不要直接使用当前系统 `node` 版本。
- 遇到旧版 `webpack`/`typescript` 工具链时，先核对仓库说明里的 Node 版本要求，再开始验证，避免把环境问题误判成代码问题。
- 用户已明确纠正：当前协作中不要为了验证去切换到低版本 Node；若仓库说明与用户要求冲突，优先遵循用户指定的当前 Node 环境，并把环境兼容性作为验证结果的一部分单独说明。
- 用户在 GPU/浏览器排查中给出的测试性 `flag`、启动参数或临时实验设置，不能直接当作根因；需要先确认它们是否只是用户为复现/测试临时加上的配置，再决定是否纳入最终结论。

## 2026-04-03

- 当用户提示 `tasks/todo.md` 或 `tasks/lessons.md` 数据丢失时，先检查当前文件、`git status` 与相关 `git log`，只恢复可证明的内容，不要凭印象重写整份历史。
- 补档任务应优先追加“恢复说明”“当前有效上下文”和“剩余风险”，而不是覆盖原有任务段落，避免再次丢失历史线索。
- 针对这个仓库的前端验证，当前仍应优先使用现有 Node 环境下可执行的 TypeScript 或静态检查；旧版 `webpack 4` 打包链兼容性另记为环境风险，不要把它误写成代码回归。
- 对浏览器或 GPU 排查结论，必须区分“放大问题的环境特征”和“已能稳定证明的根因”，没有对照样本前不要把相关性写成结论。
- 用户已明确补充：旧 Trace 只是历史复现样本；当前任务的重点是评估现阶段代码是否能改善同类问题，不能把旧 Trace 直接当成当前版本的实测结果。
- 用户已明确排除虚拟滚动作为主方案；后续应优先寻找降低单次消息更新影响面的办法，而不是把成本转移到滚动阶段。
- 用户已明确纠正：即使“新消息接收”路径做了优化，实际体感仍可能在“发言时”卡；后续不能把“发言卡”自动等同于“日志接收卡”，必须同时检查输入、发送回调、页面整体重渲染和日志回显链路。
- 用户再次明确纠正后，定位必须继续收紧到“点击发送后，自己的发言回显落到日志里的那一瞬间卡”；后续不要再把问题泛化成“输入卡”或“任意新消息卡”。
- 新 Trace 若已经明确给出“发送”和“筛选”两类卡顿的热点拆分，后续修复必须分别命中：
- 发送回显侧优先看 React 更新遍历和日志插入路径。
- 筛选侧优先看样式失效、布局与预绘制成本；不要再只盯着 JS 或 socket。

## 2026-04-07

- 用户若明确否定“拆开读取”“延后回填”“类似虚拟滚动”的方向，必须立即撤掉该方向上的新增改动，不能再把它当作过渡性缓解继续保留。
- 当用户明确判断“更像 React 渲染 bug”时，下一轮排查要直接聚焦 React commit、组件重复 mount/update、props 稳定性和 store 更新扇出，不要继续把主精力放在日志渐进渲染调度上。
- 当用户明确否定整条优化线并要求“基本都回退”时，不要只回退最后一轮补丁；应先按主题识别整条问题线上的相关代码改动，再整体回到当前 `HEAD` 基线附近重新设计。
- 如果现有 Trace 结论来自已经带改动的脏工作树，只能把它当作“错误方向的证据”和热点提示，不能直接沿用同一实现思路继续堆补丁。
- 用户已明确要求“尽量少改动”且“不继续靠 contain 规避”，后续需要优先考虑行为收缩、更新范围收缩和数据提交时机，而不是继续扩展日志分段、容器隔离等大改方案。
- 用户给出的稳定复现步骤必须严格按顺序执行；这次 418 房间卡顿的正确顺序是“先刷新房间，再打开 `chrome://flags`，关闭后返回房间触发操作”，不能自行交换“刷新”和“开 flags”的先后。
- 用户已再次明确否定“把日志切成小段”这条优化线；后续不能再把分段/分块当主方案，而应继续下探到单条 `log` 组件层面的 React 渲染与更新方式。
- 即使已经把规则面板挤压和日志头插入这两处显性问题改掉，只要用户明确反馈“发送消息时依然特别卡”，就必须立刻回到浏览器性能录制；不能把已有局部改进误当成整条发送回显链路已经解决。
- 如果发送回显 Trace 里在同一长任务内出现“恰好等于 `periodLogNumber` 的 `jf-log` 节点插入”，优先怀疑不是新消息本身，而是 `LogsRenderingState` 的历史日志后台补渲染混进了交互窗口。
- 针对这个仓库的大日志场景，历史日志回填需要与用户交互解耦；至少要在 `visibilitychange`/点击/按键后暂停一段时间，并避免继续用固定 `100` 条的大批量回填。
- 当发送 trace 更像 React 渲染问题时，先检查顶层 `observer` 是否把巨大的日志子树包在一起；如果 `getjobinfo` 一类更新会替换 `rule/icons/roleInfo/gameInfo` 引用，优先把日志区抽成带自定义比较的 `React.memo` 子树，先切断“无关 store 更新拖整片日志一起 render”这条链。
- 在 watch/dev 模式下，trace 里如果还出现 `/_serveDev/system?...` 的后续长任务，先结合交互 `INP` 判断它是否真的落在用户可感知窗口里；不要把 dev runtime 噪音直接误判成这次页面卡顿根因。

## 2026-05-24

- 这个仓库从 React16/17 迁到 React18 时，`i18n.t` 一类依赖实例 `this` 的旧方法不能直接当普通函数透传；一旦在自定义 HOC/Hook 里丢了绑定，运行时会在页面里报 `translator` 为 `undefined`。
- `createRoot` 会把旧页面初始化链路里的时序问题放大出来；如果页面在首次 commit 之前就会收到 MobX/socket 更新，优先让首次挂载走同步提交，再继续收缩真正的 render 副作用。
- React18 下要重点排查“render 里调 `setTimeout` 再 `setState`”这类旧写法；即使过去能跑，也很容易在并发挂载阶段变成 “Can't perform a React state update on a component that hasn't mounted yet”。
- 迁移阶段要先区分“阻塞运行的异常”和“旧三方库开发期警告”；前者必须立即修，后者可以在页面重新可用后再单独排期。
- 浏览器 `issue` 面板里如果只剩 `CORB/ORB`，要先定位它究竟是项目脚本、第三方 SDK 还是外链图片源；不要把所有控制台 issue 都误归因到 React 升级。
- 像微博 SDK 这类第三方脚本，如果当前环境并未启用对应功能，就不要在模板层全站无条件注入；开发环境的无效第三方噪音会明显干扰真正的运行时排查。
- 用户可配置头像这类跨站图片源，即使给 `img` 补 `referrerPolicy=\"no-referrer\"` 也不保证能绕过 Chromium `ORB`；如果源站本身返回了错误内容，根治方案应转向“图片代理”或“头像源白名单”，而不是继续在 React 渲染层兜圈子。
- 这个仓库前端 `watch` 下的动态 chunk 很容易被旧标签页缓存住；如果刚修过 webpack 分包、peer 依赖或动态 import 相关问题，必须新开页面或用隔离上下文复测，不能只看原标签页，否则会把陈旧坏 chunk 误判成源码仍未修好。
- `pug-loader` 在 `front` 目录执行时不能依赖根目录偶然 hoist 出来的 `pug`；凡是开发态 `watch` 也要走到的 peer 依赖，都要在 `front/package.json` 里显式声明并配套一条可独立运行的构建校验脚本。

## 2026-06-01

- 针对日志区筛选和新发言卡顿，优先避免按用户 ID 生成动态 CSS 选择器；把筛选状态落到稳定 class 上，能减少 `styled-components` 动态规则和属性选择器匹配的放大风险。
- 如果 trace 中出现 `StyleInvalidatorInvalidationTracking` 指向 `父:hover 子` 选择器，先把这类跨层级 hover 联动收缩掉，再评估是否还需要更大范围的渲染结构改造。
- 当筛选状态已经能在 React 渲染层计算时，不要继续给日志每个子节点保留用于 CSS 筛选的 `data-userid`；冗余 DOM 属性会扩大样式匹配和节点更新面。

## 2026-06-02

- 新日志 trace 若最大耗时仍在 `Browser/CrBrowserMain` 的空 `RunTask` 或 `UpdateLayer`，且 renderer 主线程只有百毫秒级 `Layout/Commit/PrePaint`，不要继续把根因写成业务 JS 或 React 单次提交。
- 对这个日志区问题，DOM 节点数和 JS listener 计数是关键指标；`71697` 节点、`16345` listener 级别已经足以让部分 Chromium/设备在输入、合成、截图或内部树维护上退化到秒级卡顿。
- CSS pickup/hover 优化只能减少放大器；若新 trace 仍有秒级 Browser 主线程阻塞，后续方案必须优先降低日志区实际挂载 DOM/组件/交互对象规模，而不是继续堆样式隔离。
- 在“不改变玩家可见样式”的约束下，优先把每个重复节点上的 hook/state/effect/portal 改成单例或模块级分发；这比直接合并 DOM 结构风险低，更适合作为第一轮深层优化。
